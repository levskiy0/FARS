# Кеш FARS и проверка оригиналов

## Настройка и запуск

```yaml
cache:
  ttl: "30d"
  cleanup_interval: "24h"
  check_originals_interval: "1m"
  check_originals_workers: 4
  invalidation_lock_timeout: "100ms"
  invalidation_token: ""
```

`check_originals_interval` задаёт частоту проверки оригиналов. В локальном
`config.yaml` уже стоит `1m`; встроенное значение и пример — `5m`.
`0` отключает monitor. Аналогичная переменная окружения:
`FARS_CACHE__CHECK_ORIGINALS_INTERVAL=1m` либо `CHECK_ORIGINALS_INTERVAL=1m`.

При старте HTTP-сервера запускаются фоновые goroutine для monitor и, если
включена, TTL-очистки. Первичная индексация начинается сразу, без ожидания
первого интервала. HTTP обслуживается параллельно. До окончания индексации
nginx ещё может отдавать существующие старые файлы.

При остановке сначала завершаются активные HTTP-запросы, затем отменяются
фоновые задачи. Lifecycle ждёт их завершения и сохраняет изменившийся manifest.
При неполной индексации снимок объединяет доступные записи с прежними сигнатурами ещё не обработанных путей. Ошибка сохранения оставляет снимок на повторную попытку и не блокирует другие фоновые задачи.

## Путь запроса и структура кеша

URL остаётся `/resize/{geometry}/{path}`. Файл остаётся по адресу
`cache_dir/{geometry}/{path}`. Версия и хеш в пути не добавляются.

Например, один оригинал `img/p/1/2/12.jpg` имеет варианты:

```text
200x200/img/p/1/2/12.jpg
400x400/img/p/1/2/12.jpg
400x400/img/p/1/2/12.jpg.webp
```

В конфигурации с `try_files` nginx читает существующий вариант напрямую.
FARS при таком попадании вообще не вызывается. Если файла нет, nginx передаёт
запрос в FARS; сервис читает оригинал, создаёт только запрошенный вариант,
записывает временный файл и делает `rename`. Затем регистрирует связь в памяти.
Полного предварительного пересоздания всех размеров нет.

Сам FARS при обращении к нему проверяет возраст кеша, время оригинала и
известную индексу метадату. Существующий расчёт HTTP ETag по байтам ответа
сохранён. Новый monitor не вычисляет хеш оригинала.

## Как строится индекс

1. Один раз обходится дерево `cache_dir`.
2. Файлы группируются по относительному пути без первой папки с геометрией.
3. Для каждого уникального пути проверяется соответствующий оригинал в
   `storage.base_dir`. Для `photo.jpg.webp` сначала проверяется точный файл,
   затем, если его нет, `photo.jpg`.
4. Сохраняются метадата оригинала и точный набор его вариантов. Обратная мапа
   позволяет убрать связь при удалении файла TTL-очисткой.
5. Отсутствующие оригиналы приводят к удалению их кешированных вариантов.
   Сигнатуры из предыдущего manifest позволяют обнаружить изменения за время
   остановки FARS. Без предыдущей сигнатуры доступно сравнение времени
   оригинала со временем ресайза.

Все 70 ГБ оригиналов обходить и читать не нужно. Индексируется только множество
оригиналов, на которые ссылаются существующие ресайзы. Размер памяти зависит
от числа оригиналов, числа вариантов и длины путей: `O(originals + variants)`.
Это полный рабочий индекс, а не LRU-пул из 10 000 элементов: вытеснение записи
оставило бы соответствующий оригинал без проверки.

## Что происходит раз в X минут

Monitor копирует список оригиналов под короткой блокировкой, затем отпускает её. Пути проверяет фиксированный пул работников: `check_originals_workers`, по умолчанию 4. Для одного оригинала не бывает двух незавершённых проверок. Зависший `os.Stat` занимает одного работника; остальные продолжают обрабатывать доступные оригиналы, в том числе на следующих тиках. Геометрия не используется для определения изменения.

Сравниваются:

- размер файла в байтах;
- `mtime` с доступной файловой системе точностью;
- на Linux и macOS — inode и `ctime`.

Изменение размера, перенос `mtime` вперёд или назад, замена inode, изменение
`ctime` или исчезновение оригинала запускают инвалидацию. Замена с прежним
размером и сохранённым `mtime` обычно обнаруживается по inode/ctime.
Если файловая система возвращает полностью прежнюю метадату, без чтения
содержимого доказать изменение невозможно. На остальных ОС используются
только размер и `mtime`.

Проверка только помечает оригинал как ожидающий инвалидации. Отдельный фиксированный пул удаляет варианты; его размер также задаётся `check_originals_workers`. Очередь подбирается каждые `min(X, 1s)`, поэтому удаление не ждёт ещё один полный интервал X. Для оригинала с занятой блокировкой действует `invalidation_lock_timeout` (по умолчанию 100 мс). Незавершённая операция остаётся в очереди; другие оригиналы продолжают обрабатываться. Этот бюджет ограничивает ожидание блокировок и работу между файловыми операциями, но не прерывает системный вызов внутри ядра. При большом числе вариантов удаление может завершиться за несколько попыток.

Если удалить файл не удалось, он остаётся в индексе с признаком незавершённой
инвалидации. Следующий обход повторяет попытку. Ошибки чтения метадаты,
отличные от отсутствия файла, логируются и не считаются удалением оригинала.
Новая запись другого размера не заменяет старую сигнатуру: иначе она могла
бы скрыть изменение от остальных вариантов.

Перед сохранением результата ресайза FARS повторно проверяет метадату
исходника. Если исходник изменился за время обработки, результат не попадает
в дисковый кеш. Уже выполняющийся запрос при внешней замене файла всё ещё
может вернуть старое изображение; изменения исходников не образуют транзакцию
с HTTP-запросами.

После удаления nginx получает промах `try_files`, и следующий запрос создаёт
актуальный ресайз по прежнему пути. TTL-очистка — отдельная задача с отдельным
интервалом: она обходит кеш и удаляет слишком старые и осиротевшие варианты.
При `cleanup_interval: "0"` nginx сам возраст файлов FARS не проверяет.

## Ошибки первичного обхода

Обнаружение файлов, проверка метадаты, удаление и сохранение manifest выполняются независимо. Неудачное чтение каталога не мешает обходу доступных соседних каталогов. Неудачная проверка оригинала сохраняет его ссылку на повторную попытку. Повторяются только ошибочные каталоги/ссылки; обработанные пути заново не обходятся. Уже зарегистрированные оригиналы проверяются, даже если первичный обход ещё не завершён.

Исчезнувшие оригиналы создают отдельную очередь удаления осиротевших вариантов. Ошибки удаления не влияют на готовность индекса. При недоступности всего корня кеша discovery остаётся незавершённым; известные из текущих запросов оригиналы продолжают проверяться.

Число работников ограничено. Если все они зависли внутри файловой системы, соответствующий пул перестанет продвигаться до возвращения системных вызовов. Новые goroutine взамен зависших не создаются. При штатной остановке ожидается завершение задач в рамках lifecycle-контекста; системные вызовы `stat`/`remove` не становятся отменяемыми от появления контекста.

## Manifest и рестарты

`cache_dir/.fars-originals-v1.json` содержит сигнатуры оригиналов и состояние
незавершённых инвалидаций. Список вариантов восстанавливается из кеша.

Manifest читается при bootstrap, а не на HTTP-запросах. При изменении индекса
он сохраняется одним JSON-снимком через временный файл и `rename` отдельной фоновой задачей с интервалом X, по окончании попытки discovery либо при штатной остановке. Если индекс не менялся, файл
не переписывается. Это последовательная пакетная запись; SQLite и отдельные
sidecar-файлы на каждый ресайз не используются.

На первом запуске, при повреждённом manifest или для записи, которая ещё не
успела попасть в снимок перед аварийной остановкой, старой сигнатуры может
не быть. В таком случае уже существующую старую картинку с сохранённым/старым
`mtime` нельзя надёжно распознать задним числом: создаётся текущая база
сравнения. При наличии сохранённой сигнатуры изменения между рестартами
обнаруживаются. Снимок использует атомарное переименование, но не обещает
durability при внезапном отключении питания.

Один каталог кеша должен обслуживаться одним пишущим процессом FARS.
Новые файлы, созданные этим процессом, регистрируются сразу. Внешний процесс,
добавляющий ресайзы напрямую, не сообщает об этом индексу: для их обнаружения
нужен новый bootstrap. Межпроцессные блокировки не реализованы.

## POST для ручной инвалидации

Маршруты `POST /cclear/{path}` и `POST /cache/invalidate` включаются только при непустом
`cache.invalidation_token`. Авторизация — `Authorization: Bearer <token>`.
Это дополнительный инструмент; фоновая проверка работает без отправителей POST.

Для включения задайте секрет в конфигурации и перезапустите FARS:

```yaml
cache:
  invalidation_token: "<ваш-секрет>"
```

В заголовке Authorization передаётся тот же секрет. При пустом токене оба
маршрута отключены и возвращают 404. Токен не следует передавать в URL.

Один оригинал, без тела запроса:

```bash
curl -X POST http://127.0.0.1:9090/cclear/img/p/1/2/12.jpg \
  -H "Authorization: Bearer $FARS_INVALIDATION_TOKEN"
```

Удаляются все размеры и выходные форматы этого оригинала. Сам оригинал не
удаляется. Можно передать путь уже удалённого оригинала. Повторный запрос
успешен: если вариантов больше нет, `variants_removed` равен нулю.
Пробелы и другие специальные символы нужно URL-кодировать ровно один раз.
Передаётся путь оригинала или настроенный rewrite-alias, не URL ресайза.

Пример успешного ответа:

```json
{"invalidated":["img/p/1/2/12.jpg"],"variants_removed":3}
```

`invalidated` содержит нормализованные пути оригиналов после rewrite,
а `variants_removed` — число действительно удалённых файлов ресайзов.
Ответ 200 с нулём удалений также считается успешным.

Коды ответа:

- `200` — очистка завершена, включая случай отсутствия ресайзов.
- `400` — некорректный путь или тело пакетного запроса; удаление не начинается.
- `401` — отсутствует или неверен Bearer-токен.
- `404` — маршрут отключён при пустом токене; GET не выполняет очистку.
- `500` — ошибка обхода/удаления; часть файлов могла быть удалена.
  После устранения причины повторите POST.

Пакетный маршрут `POST /cache/invalidate` сохраняет прежний JSON:

```json
{"paths":["img/p/1/2/12.jpg","img/cb/42.jpg"]}
```

Передаются пути оригиналов относительно `storage.base_dir`, без геометрии и
без выходного суффикса формата. Применяются настроенные rewrite-правила.
Пакетный запрос ограничен 64 КиБ и 1000 путями. Все пути проверяются до начала удаления;
повторы объединяются. Ответ содержит `invalidated` и `variants_removed`.

Если запись ещё не попала в индекс, ручной вызов может отдельно обойти кеш.
Обычный периодический monitor этого не делает. При ошибке удаления возвращается
500; часть файлов к этому моменту уже могла быть удалена.

## Внешний nginx и браузер

Удаление файла инвалидирует общий файловый кеш, который nginx обслуживает
через [try_files](https://nginx.org/en/docs/http/ngx_http_core_module.html#try_files).
FARS должен видеть тот же volume и иметь право удалять его файлы.

Если включён [open_file_cache](https://nginx.org/en/docs/http/ngx_http_core_module.html#open_file_cache),
nginx может ещё держать открытый дескриптор; влияет `open_file_cache_valid`.
Если другой nginx использует
[proxy_cache](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_cache_valid),
это отдельная копия HTTP-ответа: для неё нужны свой срок жизни или purge.
Джоба FARS не выполняет purge внешнего nginx/CDN.

В проверенном локальном `citimarinestore/nginx.conf` используется `try_files`
и установлены `expires 1y` / `immutable`. Браузер с уже сохранённым ответом
может не обратиться к nginx после удаления файла. Для гарантированного
обновления у клиента нужны согласованные HTTP TTL/revalidation/purge на
всех слоях. Настройки nginx и текущие Cache-Control заголовки FARS в этой
реализации не изменены.

## Замеры

Read-only диагностический тест на локальных данных обнаружил 1624 ресайза,
1164 уникальных путей кеша, 896 используемых оригиналов, 1597 связанных
вариантов и 27 вариантов без оригинала.

В трёх последовательных запусках: первичная диагностическая индексация
56–230 мс, повторная проверка 896 оригиналов — 1–3 мс. Это локальные измерения
с частично прогретым файловым кешем ОС, не оценка холодного production-диска.
Тест не удаляет реальные файлы и не создаёт manifest.

Диагностический тест хранит упрощённую мапу оригиналов; его замер памяти
132–143 КиБ не равен потреблению рабочего Manager, который также хранит
точные связи с вариантами и обратный индекс.

```bash
FARS_SCAN_BASE_DIR=/path/to/site \
FARS_SCAN_ORIGINALS_DIR=/path/to/site/img \
FARS_SCAN_CACHE_DIR=/path/to/cache \
go test -tags=integration ./internal/cache -run '^TestScanOriginalsAndResizes$' -count=3 -v
```

Логи `cache discovery progress` показывают завершённость индексации, число оригиналов/вариантов и количество каталогов/ссылок, ожидающих повторной попытки. `cache monitor progress` для проверок и удалений показывает завершённые и ошибочные задачи, число выполняющихся и ещё не выданных задач, а также возраст самой старой выполняющейся задачи (`oldest_in_flight`). По этим значениям на целевом диске выбираются X и число работников.

## Проверки и ревью инвалидации

Добавлены проверки изменений размера, mtime в обе стороны, перезаписи того же
размера с сохранённым mtime (по ctime, если его предоставляет ОС), удаления
оригинала и замены его каталогом. Проверяется удаление всех геометрий/форматов,
сохранность чужих и неизменённых ресайзов, а также новой генерации после очистки.

Интеграционный тест создаёт настоящие PNG в временных каталогах, генерирует
PNG/WebP через HTTP, заменяет оригинал и без новых GET ждёт удаления файлов
фоновой джобой. Затем тот же resize URL возвращает новые байты и ETag.
Отдельно тот же цикл проверяется через POST без запущенного monitor.
Реальные production-файлы и конфигурация nginx не затрагиваются.

При ревью исправлено и закреплено регрессионными тестами:

- Некорректный путь с NUL мог вызвать 500 после удаления предыдущих путей
  пакетного запроса. Теперь NUL и абсолютный результат rewrite отклоняются
  до начала удаления.
- Отложенная orphan-задача могла удалить уже заново созданный ресайз.
  Проверка очереди и регистрации теперь выполняется под блокировкой файла
  перед удалением, совместно с защитой публикации нового ресайза.

Остающиеся ограничения надёжности:

- Без сохранённой старой сигнатуры (первый запуск, повреждённый/утраченный
  manifest, авария до сохранения новой записи) смена оригинала с сохранённым
  mtime может остаться нераспознанной при bootstrap. Для строгой гарантии
  потребуется консервативно удалять варианты с неизвестной базой сравнения.
- Монитор гарантирует проверку зарегистрированных зависимостей этого процесса.
  Внешние записи в cache_dir после bootstrap не обнаруживаются автоматически;
  несколько писателей требуют отдельной межпроцессной координации.
- Ошибка ручного discovery или удаления возвращает 500 и допускает частичную
  очистку. Зарегистрированные варианты остаются pending; найденные только
  ручным обходом, но ещё не зарегистрированные варианты не имеют гарантии
  фонового повтора. После устранения ошибки следует повторить POST.
- Файловая инвалидация не очищает внешние HTTP-кеши. Срок X — интервал
  планирования, а не жёсткий deadline: очередь, права доступа и зависание
  файловой системы могут увеличить задержку.

Команды проверки:

```bash
go test -race ./...
go vet ./...
go test -race ./internal/cache ./internal/httpapi -run 'TestScanInvalidatesOnlyChangedOriginal|TestQueuedOrphanCannotDeleteRegeneratedResize|TestClear|TestInvalidationRejectsNUL' -count=10
go test -race -tags=integration ./internal/httpapi -run '^TestResizeInvalidationLifecycle$' -count=5
```

Результат проверки реализации: общий набор тестов с `-race` и `go vet`
прошли; выбранные регрессионные тесты прошли 10 повторов, полный цикл
PNG/WebP через сканер и POST — 5 повторов. Linux-версия тестового бинарника
пакета cache также успешно собрана кросс-компиляцией; запуск на Linux
этой проверкой не выполнялся. Эти результаты не заменяют проверку
доступа к общему cache volume и поведения внешнего nginx на целевом сервере.

Нотация resize API, пути кеша и настройки внешнего nginx не изменены.
Проверки выполнялись на временных данных: рабочие изображения не удалялись,
работающий сервис не перезапускался.
